\section{Backend Tests} \label{sec:backend_tests}
\paragraph{}We adopted a layered testing approach to validate the behavior of the system at different levels. The tests written across the solution aim to verify that the main application functions behave as expected, both in isolation and when integrated with other components. This testing approach helps identify regressions earlier, supports maintainability and provides a safer basis for future code changes.

\subsubsection{Unit Tests}
\paragraph{}For the domain logic implemented in the Service Layer, unit tests were written using Moq to isolate external dependencies, such as database repositories and infrastructure-related components. These tests validate:

\begin{itemize}
\item Domain validation rules, such as preventing empty, whitespace-only or overly long conversation tag names.
\item Behavior in edge cases, such as attempting to tag a conversation where the user is not an active participant, or modifying tags that belong to other users.
\item Error handling using typed results through the \texttt{OneOf} library pattern.
\end{itemize}

To keep the test suites maintainable and reusable, they were structured using xUnit's \texttt{IClassFixture<T>} interface. A fixture class was created for each relevant service, such as the \texttt{ConversationTagServiceFixture}.

\begin{lstlisting}[caption={ConversationTagServiceFixture instantiation}, label={lst:conversation-tag-fixture-init}]
public class ConversationTagServiceTests : IClassFixture<ConversationTagServiceFixture>
\end{lstlisting}

Implementing centralized class fixtures provides the following benefits:

\begin{itemize}
\item \textbf{Mock configuration:} Pre-configures the required dependencies, mock states and repository contexts, such as \texttt{IConversationTagRepository}, \texttt{IUserRepository} and \texttt{IConversationRepository}, within a centralized setup constructor.
\item \textbf{Transaction setup:} Simulates transactional behavior through the \texttt{ITransactionManager}, allowing service methods that depend on transaction handling to be tested in isolation.
\item \textbf{Reusable helper methods:} Exposes helper methods, such as \texttt{SetupTagNameExists(bool)} and \texttt{SetupUserIsParticipant(bool)}, allowing individual test cases to configure the expected mock behavior in a consistent way.
\end{itemize}


\begin{lstlisting}[caption={Unit test execution inside ConversationTagServiceTests}, label={lst:conversation-tag-unit-tests}]
[Fact]
public async Task CreateTag_ShouldReturnError_WhenTagNameAlreadyExists()
{
    // Arrange
    _fixture.SetupUserExists(true);
    _fixture.SetupTagNameExists(true);
    _fixture.SetupCreateTag(10);

    // Act
    var result = await _fixture.ConversationTagService.CreateTag(_fixture.UserId, "Duplicada", "#FFFFFF");

    // Assert
    Assert.True(result.IsT1); // Validates that a failure union state was reached
    Assert.IsType<ConversationTagError.TagNameAlreadyExists>(result.AsT1);
}
\end{lstlisting}

As illustrated in Listing~\ref{lst:conversation-tag-unit-tests}, the test uses fixture methods to configure the required scenario before executing the service method. In this case, the mock setup defines that a tag with the same name already exists. As a result, the service returns a domain error instead of creating a new tag.

The application uses \texttt{OneOf} to represent operation results, including both success and error cases. The test verifies that the returned result corresponds to an error state through \texttt{IsT1} and confirms that the specific error is \texttt{ConversationTagError.TagNameAlreadyExists}.
