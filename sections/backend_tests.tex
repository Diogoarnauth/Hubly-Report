\section{Backend Tests}
We adopted a layered testing approach to ensure high confidence in our system’s behavior. With over 200 tests written, our goal was to validate that every function in the application performs exactly as intended — both in isolation and when integrated with other components. This rigorous test coverage helps us identify regressions early, improve maintainability, and confidently refactor code.

\subsubsection{Unit Tests}
For business logic in the Service Layer, we wrote extensive unit tests using Moq to mock all external dependencies, such as repositories and configuration settings. These tests validate:
BOLACHA
\begin{itemize}
    \item Business rules (e.g., category name length)
    \item Behavior under edge cases (e.g., icon not found, user not in wallet)
    \item Correct handling of internal operations (e.g., transactions)
\end{itemize}

We structured these using the XUnit \texttt{IClassFixture<T>} interface and created a reusable Fixture class per service, for example:
\begin{lstlisting}[caption={CategoryServiceFixture}, label={lst:category-service-fixture}]
public class CategoryServiceTests : IClassFixture<CategoryServiceFixture>
\end{lstlisting}

This allows us to:
\begin{itemize}
    \item Set up reusable mocks for dependencies (ICategoryRepository, IWalletRepository, etc.)
    \item Provide consistent test data (TestCategory, TestIcon)
    \item Easily toggle between different states (e.g., user has/hasn't access, category is default)
\end{itemize}

\begin{lstlisting}[caption={CategoryServiceTests}, label={lst:category-service-tests}]
[Fact]
public async Task GetAllCategories_ShouldReturnCategories_WhenUserHasAccess()
{
    var result = await _fixture.CategoryService.GetAllCategories(
        _fixture.UserId,
        _fixture.WalletId,
        10,
        0
    );

    Assert.True(result.IsT0); // Ensure we got a list of categories
    Assert.NotEmpty(result.AsT0); // There should be at least one

    _fixture.WalletRepository.Verify(x =>
        x.UserIsPartOfWallet(_fixture.WalletId, _fixture.UserId), Times.Once);
}
\end{lstlisting}


\subsubsection{Integration Tests}
To validate the correctness of our data access layer—particularly Entity Framework queries—we implemented a suite of integration tests targeting the repository layer. These tests interact with a real PostgreSQL database instance to ensure:

\begin{itemize}
\item Queries return accurate and expected results
\item Entity mappings between \texttt{C\#} classes and database tables are correctly configured
\item Transactional operations behave as intended, including commit and rollback scenarios
\end{itemize}

We leveraged \texttt{Testcontainers}, a .NET library that enables programmatic management of lightweight Docker containers, to create a fully isolated and disposable test environment. This approach offers several key benefits:

\begin{itemize}
\item Automatic provisioning of a dedicated PostgreSQL container per test class
\item Clean and predictable database state through controlled data seeding
\item Complete isolation from development and production databases
\end{itemize}

The following snippet demonstrates how integration tests are structured using Testcontainers:

\begin{lstlisting}[caption={Integration Test Using Testcontainers}, label={lst:integration-test}]
public class CategoryRepositoryTests : IClassFixture<CategoryContainerFixture>
{
[Fact]
[Trait("Category", "Integration")]
public async Task GetAllCategories_ShouldReturnCategories_WhenWalletHasCategories()
{
    await _fixture.ExecuteInTransactionAsync(async () =>
    {
        var categories = await _categoryRepository.GetAllCategories(1, 10, 0);

        Assert.NotNull(categories);
        Assert.NotEmpty(categories);
        Assert.All(categories, c => Assert.NotNull(c.Icon));
    });
}
}
\end{lstlisting}

This setup ensures that each test executes against a real, fully isolated PostgreSQL instance with seeded test data, offering confidence in the correctness of the data access layer under real-world conditions.
