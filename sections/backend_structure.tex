\subsection{Design Principles and Patterns}

\paragraph{}To ensure robustness in error management, our API adopts the Problem Details for HTTP APIs standard (RFC 9457) \cite{rfc9457}. This specification allows the backend to communicate errors through structured, consistent responses, replacing ambiguous exceptions with clear, machine-readable diagnostic information.

The backend is organized into distinct layers to promote maintainability, scalability, and a strict separation of concerns. This modular approach allows for the isolated development and evolution of different system components:

\begin{itemize}
\item \textbf{Controllers}: Act as the entry point, managing incoming HTTP requests and orchestrating the appropriate responses.
\item \textbf{Services}: Encapsulate the core business logic, ensuring that domain rules are applied independently of the presentation layer.
\item \textbf{Repositories}: Define the data access layer, abstracting database interactions and shielding the business logic from persistence-specific details.
\end{itemize}

Furthermore, to uphold data consistency and integrity across complex operations, we implemented a \textbf{Transaction Manager}. This component ensures the atomicity of database interactions by grouping multiple operations into a single logical unit. Consequently, all operations within a transaction are committed only if entirely successful; otherwise, the system triggers a rollback, effectively preventing the database from entering an inconsistent state.
\subsection{Authentication and Authorization Pipeline} \label{subsec:auth_pipeline}

To enforce strict security boundaries across the Hubly API, most endpoints are protected by a centralized interception mechanism that validates both user authentication and account activation status before any business logic is executed. Specifically, the system mandates that every inbound request to a protected resource must originate from a legitimate, active session belonging to a user who has successfully verified their email address.

\subsubsection{Pipeline Architecture and Lifecycle Integration}
This validation process is enforced through a custom action filter, \texttt{RequireAuthenticationAttribute}, which integrates directly into the ASP.NET Core request lifecycle. Working in conjunction with a specialized \texttt{TokenProcessor} service, this filter forms a unified validation and dependency injection pipeline comprised of four distinct phases:

\begin{enumerate}
    \item \textbf{Identity Resolution:} The pipeline acts as a transparent hybrid interface, dynamically retrieving the authentication token from either the HTTP request headers or the application's secure cookies (supporting web clients).
    \item \textbf{Cryptographic Token Validation:} The \texttt{TokenProcessor} decrypts and evaluates the structural integrity, signature, and expiration date of the extracted token, ensuring that the current session is active and untampered with.
    \item \textbf{Authorization and Account Status Enforcement:} Beyond validating cryptographic credentials, the pipeline evaluates domain-specific state requirements. It explicitly verifies the user's account status by inspecting the email confirmation status. If the email remains unverified, the pipeline abruptly terminates the execution flow and returns a \texttt{403 Forbidden} error following the RFC 7807 Problem Details specification, preventing unconfirmed accounts from accessing core operations.
    \item \textbf{Identity Binding and Dependency Injection:} Once authentication and authorization criteria are fully satisfied, the filter instantiates an \texttt{AuthenticatedUser} object containing the user's resolved identity metadata and caches it within \texttt{HttpContext.Items}. To streamline downstream consumption, a custom \texttt{AuthenticatedUserModelBinder} intercepts the controller parameter instantiation, automatically mapping this object directly into method signatures.
\end{enumerate}

This declarative design offers substantial architectural advantages over traditional ad-hoc verification patterns:
\begin{itemize}
    \item \textbf{Centralized Logic:} All identity mapping and state guarding rules are consolidated within a single, cohesive engine, eliminating repetitive cross-cutting authentication code across endpoints.
    \item \textbf{Separation of Concerns:} Controller actions remain entirely decoupled from identity checks, allowing them to focus exclusively on executing core business rules.
    \item \textbf{Declarative Security:} Security boundaries are explicitly declared via controller method signatures using the \texttt{AuthenticatedUser} parameter. This self-documenting pattern greatly improves readability and simplifies architectural security audits.
\end{itemize}


\subsubsection{Cookie Configuration and Session Security}
\paragraph{}For web-based client applications, session persistence is managed using strict cookie policies to prevent token theft. Listing~\ref{lst:login-response} highlights the programmatic configuration applied when appending the session cookie to the outbound HTTP response:

\begin{lstlisting}[caption={Authentication Cookie Configuration}, label={lst:login-response}]
var cookieOptions = new CookieOptions
{
    HttpOnly = true,
    Secure = false, // Must be configured as true in production environments
    SameSite = SameSiteMode.Strict,
    Expires = DateTime.Now.AddDays(7)
};
Response.Cookies.Append("token", tokenValue, cookieOptions);
\end{lstlisting}

This setup follows industry-standard security baselines to safeguard tokens at rest within the user's browser:
\begin{itemize}
    \item \textbf{\texttt{HttpOnly}:} Prevents client-side scripts from accessing the cookie value via \texttt{document.cookie}, creating a robust defense mechanism against Cross-Site Scripting (XSS) attacks.
    \item \textbf{\texttt{SameSite (Strict)}:} Restricts the browser from sending the cookie along with cross-site requests, mitigating Cross-Site Request Forgery (CSRF) attempts by ensuring the payload is only transmitted on requests originating natively from the application's domain.
    \item \textbf{Persistence Policy:} Establishes a 7-day expiration boundary, balancing user convenience with session lifecycle security.
\end{itemize}
\subsection{Error Handling Middleware}

\paragraph{}A cornerstone of our error management strategy is the global error-handling middleware, which serves as a protective layer between the core application logic and the client-side response. This component is designed to ensure that unexpected faults are captured and communicated in a standardized, predictable manner.

\begin{lstlisting}[caption={Error Handling Middleware Implementation}, label={lst:error-handling-middleware}]
private static async Task HandleExceptionAsync(HttpContext context, Exception exception)
{
var statusCode = (int)HttpStatusCode.InternalServerError;
context.Response.ContentType = "application/problem+json";
context.Response.StatusCode = statusCode;

    var problem = ProblemResponse.InternalServerError;

    var json = JsonSerializer.Serialize(problem);
    await context.Response.WriteAsync(json);
}
\end{lstlisting}

As illustrated in Listing~\ref{lst:error-handling-middleware}, this middleware fulfills two primary architectural roles:

\begin{itemize}
\item \textbf{Global Exception Interception}: It acts as a safety net, capturing any unhandled exceptions during request execution—such as database connectivity issues or unforeseen system failures. By intercepting these faults, the middleware prevents raw or sensitive stack trace information from propagating to the client, which significantly hardens the API against information disclosure.

\item \textbf{Standardized Response Mapping}: The middleware transforms intercepted exceptions into well-defined responses conforming to the \texttt{application/problem+json} format (RFC 9457). This ensures that error reporting remains consistent across the entire system, providing clients with a reliable and easily consumable interface for handling failures.
\end{itemize}

Technically, the implementation enforces a 500 Internal Server Error status code by default for unhandled faults. It then serializes a predefined ProblemResponse object into JSON, ensuring the output adheres strictly to our established API error contract, thereby maintaining seamless communication with the frontend.


\subsection{Email Service}

\paragraph{}The system incorporates a dedicated email service primarily to orchestrate user identity verification. By requiring users to validate their registration via a unique verification code, we significantly enhance platform security and ensure that all accounts are linked to accessible, legitimate email addresses.

The verification workflow operates as follows:
\begin{itemize}
\item \textbf{Token Generation}: Upon registration, the system automatically generates a unique, time-sensitive verification code.
\item \textbf{Secure Dispatch}: The email service transmits this code to the user's provided email address.
\item \textbf{Identity Confirmation}: The user is required to input the received code within the application to finalize the account activation process.
\end{itemize}
