\subsection{Design Principles and Patterns}

\paragraph{}To ensure robustness in error management, our API adopts the Problem Details for HTTP APIs standard (RFC 9457) \cite{rfc9457}. This specification allows the backend to communicate errors through structured, consistent responses, replacing ambiguous exceptions with clear, machine-readable diagnostic information.

The backend is organized into distinct layers to separate request handling, business logic and data access. This organization supports maintainability and makes the responsibilities of each component clearer:

\begin{itemize}
\item \textbf{Controllers}: Act as the entry point, managing incoming HTTP requests and orchestrating the appropriate responses.
\item \textbf{Services}: Encapsulate the core business logic, ensuring that domain rules are applied independently of the presentation layer.
\item \textbf{Repositories}: Define the data access layer, abstracting database interactions and shielding the business logic from persistence-specific details.
\end{itemize}

Furthermore, the backend also includes a \textbf{Transaction Manager}, used in operations that require multiple database changes to be handled as a single unit. This component ensures the atomicity of database interactions by grouping multiple operations into a single logical unit. Consequently, all operations within a transaction are committed only if entirely successful, otherwise, the system triggers a rollback, effectively preventing the database from entering an inconsistent state.

\subsection{Project Structure and Dependency Management} \label{subsec:project-structure}

\paragraph{} The backend solution is organized into four distinct .NET projects, each defined by an individual \texttt{.csproj} file and managed with its own set packages. This organization defines the architectural boundaries of the backend and makes the dependency structure explicit at compilation time:

\begin{description}
    \item[\textbf{Hubly.Domain}:] Acts as the system core, containing exclusively the business entities and domain models. It is designed to be agnostic of any persistence technology or framework, maintaining independence from the other solution layers.

    \item[\textbf{Hubly.Infrastructure}:] Implements the data access layer. It contains the concrete repository implementations, their corresponding interfaces, and the \texttt{HublyDbContext}. The latter serves as the primary bridge to the database, configuring the mapping between domain entities and PostgreSQL tables via Entity Framework Core.

    \item[\textbf{Hubly.Services}:] Contains the application services and their respective interfaces, which orchestrate the business logic. This project also includes specialized components such as password/token encoders (handling cryptographic hashing and salting), domain-specific error definitions (\textit{DomainErrors}) used for result validation, and the backend unit test suite.

    \item[\textbf{Hubly.Api}:] Functions as the application entry point (\texttt{Microsoft.NET.Sdk.Web}). It manages the interaction with external clients through controllers and Data Transfer Objects (DTOs). This project also encapsulates the cross-cutting concerns of the web layer, including the global exception handling middleware, the authentication/authorization pipeline, the \texttt{ProblemResponse} definitions, and the URI routing configurations.
\end{description}

\paragraph{} The dependency graph follows a unidirectional flow. This structure prevents circular dependencies by ensuring that inner layers (Domain) remain isolated, while infrastructural concerns are encapsulated within \texttt{Infrastructure} and \texttt{Api}. Furthermore, this separation facilitates maintenance and supports isolated unit testing by allowing the replacement of infrastructure components with mocks via the \texttt{Moq} framework.

\subsection{Application Composition and Dependency Injection} \label{subsec:app-composition}

\paragraph{} The composition of the Hubly API is centralized in the \texttt{Program.cs} file, which serves as the application's entry point and the Composition Root. This file is responsible for configuring the Dependency Injection (DI) container, the mechanism that wires together the distinct layers defined in the project structure. The configuration process manages several architectural concerns:

\begin{itemize}
    \item \textbf{Service Registration}: The DI container maps interfaces to their concrete implementations (e.g., \texttt{IUserService} to \texttt{UserService}), decoupling the consumer from the implementation. This ensures that the layers interact exclusively through defined abstractions.
    
    \item \textbf{Infrastructure Initialization}: The database context (\texttt{HublyDbContext}) is initialized and configured with the PostgreSQL provider, establishing the link between the domain entities and the underlying storage.
    
    \item \textbf{Pipeline Configuration}: The HTTP request pipeline is structured to process incoming traffic through a specific sequence of middlewares and filters. This includes the global \texttt{ExceptionMiddleware} for standardized error reporting, CORS policies for origin security, and the registration of the \texttt{RequireAuthenticationAttribute} as a global filter to enforce security boundaries.
    
    \item \textbf{Cross-Cutting Concerns}: Registration of singleton domain configuration objects and mapping profiles (using \textit{Mapster}) ensures consistent data transformation between domain entities and Data Transfer Objects (DTOs).
\end{itemize}

\paragraph{} This centralized approach ensures that all dependencies are resolved at runtime, reinforcing the isolation between layers and allowing for the integration of new services without modifying the core business logic.


\subsection{Authentication and Authorization Pipeline} \label{subsec:auth_pipeline}

\paragraph{}To enforce strict security boundaries across the Hubly API, most endpoints are protected by a centralized interception mechanism that validates both user authentication and account activation status before any business logic is executed. Specifically, the system mandates that every inbound request to a protected resource must originate from a legitimate, active session belonging to a user who has successfully verified their email address.

\subsubsection{Pipeline Architecture}
\paragraph{}The authentication process is implemented through a action filter, \texttt{RequireAuthenticationAttribute}, which is executed during the ASP.NET Core request pipeline. This filter works together with the \texttt{TokenProcessor} service to validate the request and provide the authenticated user information to the controller.
The process is organized into the following steps:
\begin{enumerate}
\item \textbf{Token extraction:} The filter obtains the authentication token from the incoming HTTP request. Depending on the client flow, the token may be read from the request headers or from the application cookies.

\item \textbf{Token validation:} The \texttt{TokenProcessor} decrypts and evaluates the structural integrity, signature, and expiration date of the extracted token, ensuring that the current session is active and untampered with.

\item \textbf{Account status validation:} After the token is validated, the filter also verifies domain-specific access conditions. In Hubly, this includes checking whether the user's email address has been confirmed. If the email is not confirmed, the request is rejected with a \texttt{403 Forbidden} response, following the Problem Details response format.

\item \textbf{Authenticated user binding:} When all validation steps succeed, the filter creates an \texttt{AuthenticatedUser} object containing the resolved user identity. This object is stored in \texttt{HttpContext.Items}, making it available during the remaining execution of the request. A custom \texttt{AuthenticatedUserModelBinder} is then used to bind this object directly to controller action parameters when required.

\end{enumerate}

This approach provides a consistent way to apply authentication checks across protected endpoints. Its main benefits are the following:
\begin{itemize}
\item \textbf{Centralized validation:} The extraction and validation of the authenticated user are handled in one reusable filter, avoiding repeated authentication logic in multiple controllers.

\item \textbf{Separation of concerns:} Controller actions do not need to manually validate the authentication token. This allows controllers to focus on the application operation they are responsible for.

\item \textbf{Declarative Security:} Security boundaries are explicitly declared via controller method signatures using the \texttt{AuthenticatedUser} parameter. This self-documenting pattern greatly improves readability and simplifies architectural security audits.

\end{itemize}

\subsubsection{Cookie Configuration and Session Security}
\paragraph{}For web-based client applications, session persistence is managed using strict cookie policies to prevent token theft. Listing~\ref{lst:login-response} highlights the programmatic configuration applied when appending the session cookie to the outbound HTTP response:
\paragraph{}
\paragraph{}
\paragraph{}
\paragraph{}
\begin{lstlisting}[caption={Authentication Cookie Configuration}, label={lst:login-response}]
var cookieOptions = new CookieOptions
{
    HttpOnly = true,
    Secure = false, // Must be configured as true in production environments
    SameSite = SameSiteMode.Strict,
    Expires = DateTime.Now.AddDays(7)
};
Response.Cookies.Append("token", tokenValue, cookieOptions);
\end{lstlisting}

This setup follows industry-standard security baselines to safeguard tokens at rest within the user's browser:
\begin{itemize}
    \item \textbf{\texttt{HttpOnly}:} Prevents client-side scripts from accessing the cookie value through \texttt{document.cookie}, reducing exposure to attacks that rely on reading cookies through JavaScript.
    \item \textbf{\texttt{SameSite (Strict)}:} Restricts the browser from sending the cookie with cross-site requests, reducing exposure to Cross-Site Request Forgery (CSRF) attacks.
    \item \textbf{Persistence Policy:} Defines a 7-day expiration period for the authentication cookie.
\end{itemize}
\subsection{Error Handling Middleware}

\paragraph{}The backend includes a global error-handling middleware responsible for capturing unhandled exceptions during request execution. Instead of returning raw exception information to the client, the middleware returns a structured response using the \texttt{application/problem+json} format.

\begin{lstlisting}[caption={Error Handling Middleware Implementation}, label={lst:error-handling-middleware}]
private static async Task HandleExceptionAsync(HttpContext context, Exception exception)
{
var statusCode = (int)HttpStatusCode.InternalServerError;
context.Response.ContentType = "application/problem+json";
context.Response.StatusCode = statusCode;

    var problem = ProblemResponse.InternalServerError;

    var json = JsonSerializer.Serialize(problem);
    await context.Response.WriteAsync(json);
}
\end{lstlisting}

As illustrated in Listing~\ref{lst:error-handling-middleware}, this middleware fulfills two primary architectural roles:

\begin{itemize}
\item \textbf{Exception Interception}: It captures unhandled exceptions during request execution, such as database connectivity errors or unexpected application failures. By handling these exceptions centrally, the middleware avoids exposing stack trace information or internal implementation details to the client.

\item \textbf{Response Mapping}: The middleware transforms intercepted exceptions into well-defined responses conforming to the \texttt{application/problem+json} format (RFC 9457). This ensures that error reporting remains consistent across the entire system, providing clients with a reliable and easily consumable interface for handling failures.
\end{itemize}

For unhandled exceptions, the middleware returns a \texttt{500 Internal Server Error} response and serializes a predefined \texttt{ProblemResponse} object into JSON. This keeps the response format consistent with the API error contract used by the frontend.


\subsection{Email Service}

\paragraph{}The backend includes an email service used during the account confirmation process. When a user registers, the system generates a verification code and sends it to the email address provided during registration. The user must submit this code in the application to confirm the account.

The verification workflow operates as follows:
\begin{itemize}
\item \textbf{Code Generation}: Upon registration, the system automatically generates a unique, time-sensitive verification code.
\item \textbf{Secure Dispatch}: The email service transmits this code to the user's provided email address.
\item \textbf{Account confirmation}: The user is required to input the received code within the application to finalize the account activation process.
\end{itemize}
