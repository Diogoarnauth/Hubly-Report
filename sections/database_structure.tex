The relational model was designed to support the functional and structural needs of a marketplace platform. Each entity and its attributes were carefully selected to reflect real-world concepts such as users, creators, creators social profiles, companies, etc. Below is an intuitive justification for the key design decisions:
\begin{itemize}
    \item \textbf{USERS}: Represents individual users of the platform. Attributes like id, name, email,  password\_validation, a flag is\_email\_confirmed, and a timestamp created\_at. This structure supports user authentication, account management, and email verification processes.

    \item \textbf{SOCIAL\_PLATFORMS}: A table to store information about different social media platforms. It works as a source of truth for social media integration. Here are only the social networks we currently support, but it can be easily extended in the future if we want to add more.

    \item \textbf{TOKEN}: Stores session or login tokens for users. Includes created\_at and last\_used\_at to support expiration and activity tracking, promoting secure authentication.

    \item \textbf{CREATORS}: Represents content creators on the platform. It includes a foreign key (that for business logic was chosen to be the PK as well) to the USER table, linking each creator to a user account. Here we also store the creator's name, description, and profile picture URL (In the future), is is\_verified flag to indicate if the creator has been verified by the platform, availability\_status, a global\_rating (as a source of reputation), and other statistics for interaction management.

    \item \textbf{COMPANIES}: Represents companies and business entities on the platform. Similarly to the CREATOR entity, it utilizes a foreign key to the USER table as its primary key (PK) to maintain a one-to-one relationship with the user account, ensuring data integrity via a cascade delete policy. This table stores essential business information, including the \texttt{company\_name}, an \texttt{is\_verified} status flag, a \texttt{description}, the \texttt{company\_size}, the \texttt{website\_link}, and the \texttt{country\_headquarters}, providing a comprehensive profile for companies seeking marketing partnerships.

    \item \textbf{SECTORS}: A table to store information about different market sectors. It works as a source of truth for companies and creators sectors. Here are only the market sectors we currently support, but it can be easily extended in the future if we want to add more.

    \item \textbf{COMPANY\_SECTORS}: Acts as an associative table to implement a many-to-many relationship between the \texttt{COMPANY} and \texttt{SECTOR} entities. By using a composite primary key consisting of \texttt{company\_user\_id} and \texttt{sector\_id}, it enables companies to be associated with multiple business sectors, facilitating granular filtering and discovery within the marketplace.

    \item \textbf{CREATOR\_SOCIAL\_PROFILES}: Stores detailed information regarding a creator's presence on specific social media platforms. Each record links to a \texttt{CREATOR} via \texttt{creator\_id} and specifies the platform through \texttt{platform\_id}. It captures essential metrics and metadata, such as \texttt{platform\_user\_name}, a \texttt{link}, \texttt{description}, \texttt{followers\_count}, and pricing ranges (\texttt{price\_min} and \texttt{price\_max}). A unique constraint on \texttt{(platform\_id, platform\_user\_name)} ensures data integrity and prevents duplicate social media accounts.

    \item \textbf{CREATOR\_PROFILE\_SECTORS}: Functions as a junction table that links individual social media profiles to specific sectors. This design allows for a multi-faceted categorization of a creator's professional niche across different platforms. By associating a \texttt{profile\_id} with a \texttt{sector\_id}, the platform can effectively index creators based on the specific content domain of each individual social channel.

    \item \textbf{EMAIL\_CONFIRMATION}: Manages the lifecycle of email verification tokens required for user account activation. This table stores the \texttt{confirmation\_code} associated with a specific \texttt{user\_id}, along with temporal constraints defined by \texttt{created\_at} and \texttt{expires\_at} (stored as \texttt{bigint} timestamps). The \texttt{used} boolean flag tracks whether a code has already been consumed. The foreign key relationship with the \texttt{USER} table ensures that verification records are automatically removed via a cascade delete policy if the corresponding user account is deleted, maintaining database consistency.

    \item \textbf{PROFILE\_VIEWS\_HISTORY}: Records the interaction history of users visiting other profiles. This table utilizes a \texttt{CHECK} constraint (\texttt{chk\_only\_one\_viewed}) to ensure that each entry refers exclusively to either a company profile or a creator social profile, maintaining a strict data normalization strategy. It captures the \texttt{viewer\_user\_id}, the specific target entity, and the timestamp (\texttt{viewed\_at}), providing the foundation for analytical insights into profile engagement and reach.

    \item \textbf{CREATOR\_RATINGS}: Manages the peer-based reputation system by storing numerical evaluations of content creators. Each record consists of an \texttt{evaluator\_id}, a \texttt{target\_creator\_id}, and a \texttt{rating\_value} (constrained to a scale of 1 to 5). The table enforces business rules through two primary constraints: \texttt{unique\_user\_rating}, which prevents multiple ratings from the same user for a single creator, and \texttt{chk\_not\_self\_rating}, which logically prohibits users from rating their own profiles.

    \item \textbf{CONVERSATIONS}: Serves as the central entity for all communication private chats. It stores metadata such as \texttt{created\_at} and \texttt{last\_message\_at}, allowing for efficient sorting and retrieval of active conversations in the messaging UI.

    \item \textbf{CONVERSATION\_PARTICIPANTS}: Maps the users involved in each conversation. It utilizes a \texttt{CHECK} constraint (\texttt{chk\_participant\_role}) to enforce that a participant acts either as a company representative or a creator social profile, effectively decoupling the user's base identity from their active role in the partnership negotiation.

    \item \textbf{MESSAGES}: Stores the actual content of communications. It supports message lifecycle tracking through boolean flags \texttt{is\_edited} and \texttt{is\_deleted}, ensuring auditability while maintaining a clean chat history. Messages are linked to a specific \texttt{conversation\_id} and identified by a \texttt{sender\_id}.

    \item \textbf{MESSAGE\_READ\_STATUS}: Manages individual delivery receipts and read state. By mapping each \texttt{user\_id} to the \texttt{last\_read\_message\_id} within a specific conversation, it enables granular tracking of message progression, ensuring that participants can identify which communications are still pending review.

    \item \textbf{CONVERSATION\_TAGS}: Allows users to create custom categorization labels for their communication chats. Each tag is owned by a specific \texttt{user\_id} and defined by a name and a \texttt{color\_hex}, enabling a personalized tag experience. The \texttt{unique\_user\_tag\_name} constraint ensures that users do not define duplicate tags within their own workspace.

    \item \textbf{CONVERSATION\_TAG\_ASSIGNMENTS}: Implements the association between a conversation and the tags assigned by a specific user. The composite primary key ensures that each conversation-tag assignment is unique per user, while \texttt{updated\_at} provides the necessary audit trail for tag modifications.

\end{itemize}

\section{Database Functions and Recommendation Engine}
\paragraph{}To ensure the high performance of our platform and minimize data transfer latency, we implemented a custom recommendation engine directly within the database layer. By offloading complex scoring algorithms to PostgreSQL, we ensure that ranking calculations are performed at the data source, returning only the most relevant, pre-scored entities. This approach leverages the engine's ability to process large datasets efficiently, moving away from traditional, resource-heavy API-side filtering.

\subsection{Company Recommendation Algorithm}
\paragraph{}The \texttt{get\_recommended\_companies} function implements a weighted multi-factor scoring algorithm to match companies with potential partners. It receives a user's interest profile as a \texttt{JSONB} object, allowing for dynamic, schema-less input. The \texttt{recommendation\_score} is derived from an additive model that applies specific weights to three distinct dimensions:
\begin{itemize}
\item \textbf{Sector Affinity (Weight 10x)}: Analyzes sector alignment between user interests and company expertise.
\item \textbf{Geographic Alignment (Weight 5x)}: Prioritizes companies based on the user's preferred country headquarters.
\item \textbf{Scale Compatibility (Weight 2x)}: Adjusts relevance based on the size of the business entity.
\end{itemize}
\paragraph{}By multiplying these inputs by predefined coefficients, the algorithm produces a prioritized ranking. Furthermore, it ensures a "fresh feed" by dynamically excluding previously viewed entities via a cross-reference with the \texttt{profile\_views\_history} table.

\subsection{Creator Social Profile Recommendation Algorithm}
\paragraph{}The \texttt{get\_recommended\_social\_profiles} function employs a sophisticated, multi-dimensional analysis to rank content creators. Unlike standard filtering, this algorithm computes a \texttt{recommendation\_score} using a nuanced scoring logic:
\begin{itemize}
\item \textbf{Domain Expertise}: High-weight aggregation of matches across creator sectors (\texttt{Weight 100x}).
\item \textbf{Platform Preference}: Boosts results based on the user's specific social channel focus (\texttt{Weight 10x}).
\item \textbf{Operational Readiness}: Direct integration of real-time \texttt{availability\_status}, providing a binary boost for active creators.
\item \textbf{Reputation Metrics}: Incorporates the creator's \texttt{global\_rating}, ensuring quality-first results.
\item \textbf{Dynamic Budget Optimization}: A conditional pricing logic that validates the creator's \texttt{price\_min} against the user’s \texttt{avg\_price} budget, providing a 20\% tolerance margin to balance affordability with value.
\end{itemize}

This approach transforms the recommendation feed from a static list into a high-utility discovery tool. By processing these weights directly in SQL, we achieve sub-millisecond ranking performance, even when evaluating diverse criteria across thousands of social profiles.
