\paragraph{}To maintain a clean separation of concerns and ensure scalability, the frontend architecture is divided into three primary directories:

\begin{itemize}
    \item \textbf{app:} This directory serves as the structural foundation of the platform, utilizing the Next.js App Router for file-system-based routing. Rather than handling imperative user navigation, it defines the URL endpoints of the application. The files within this directory act as lightweight entry points that extract URL parameters, define route-specific layouts, wrap pages with necessary Context Providers (such as injecting a \texttt{SignalRProvider} for chat routes), and delegate the actual UI rendering and complex logic to dedicated components.
    \item \textbf{components:} This folder acts as a repository for modular, reusable User Interface (UI) elements. It isolates the visual building blocks from the core routing logic.
    \item \textbf{services:} Centralizes all external communications. This directory handles API requests, data fetching, and core business logic, ensuring that UI components remain lightweight and focused solely on rendering data.
\end{itemize}

\section{Components Architecture}
\paragraph{}Components define the main building blocks of the frontend. They were organized to reduce dependency on specific pages and to support reuse across different parts of the application.

The components folder follows a modular organization to improve code maintainability. General-purpose elements that appear across multiple views, such as buttons and form inputs, are centralized in the \texttt{ui} subdirectory. The \texttt{shadcn/ui} library was used for these shared components, supporting consistency across common interface elements.

Components associated with specific features are grouped into dedicated folders. For example, the \texttt{chat} and \texttt{search} directories contain components such as \texttt{ChatDashboard} and \texttt{CreatorSearch}. This organization helps keep feature-related components separated and easier to locate.
\section{Global State and Contexts} \label{sec:contexts_web}

\paragraph{}In our application, certain data must be instantly accessible across almost every view. The most critical piece of global information is the authenticated user's session data (specifically their \texttt{id}, \texttt{name}, and \texttt{role} as a creator or company). This information is heavily utilized by global components like the \texttt{Navbar}, which adapts its UI and navigation links based on the active user profile.

To avoid repeatedly requesting the same user information from the backend on each page load, the frontend combines React’s Context API with \textbf{TanStack React Query}. React Query is used to fetch and cache server-side data, while React Context makes selected state available to components that need it.

\subsection{Server State Caching with React Query}
\paragraph{}React Query is used for server-state management. As demonstrated in the \texttt{UserProvider}, the \texttt{useQuery} hook fetches the current user's basic information. React Query caches this response. By configuring a \texttt{staleTime} of 30 minutes, the application can reuse the cached user data during navigation instead of requesting it from the backend on every page change.

\begin{lstlisting}[caption={UserProvider utilizing React Query}, label={lst:user-provider}]
export const UserProvider = ({ children }: { children: React.ReactNode }) => {
    const queryClient = useQueryClient();

    const { data: user, isLoading, refetch } = useQuery({
        queryKey: ['user'],
        queryFn: async () => {
            const userData = await usersService.getCurrentUser();
            return userData ? {
                id: userData.id,
                name: userData.name,
                email: userData.email,
                role: userData.role 
            } : null;
        },
        staleTime: 1000 * 60 * 30, // Maintains data fresh for 30 minutes
        retry: false,
    });
    // ...
};
\end{lstlisting}

\subsection{Context Distribution}
\paragraph{}After React Query fetches and caches the data, React’s Context API is used to make it available throughout the component tree. A \texttt{UserContext} was created together with a custom hook named \texttt{useUser}. This abstraction allows components, such as the Navbar, to access the user object, loading state and authentication-related methods, such as \texttt{logout} or \texttt{refreshUser}, without passing props through multiple component levels.

To make these contexts available across the application, they are centralized in a \texttt{Providers} wrapper. This wrapper includes the \texttt{QueryClientProvider}, \texttt{ThemeProvider} and \texttt{UserProvider} around the Next.js \texttt{RootLayout}.

\begin{lstlisting}[caption={Global Providers Setup}, label={lst:providers-setup}]
export function Providers({ children }: { children: React.ReactNode }) {
  const [queryClient] = useState(() => new QueryClient());
  return (
    <QueryClientProvider client={queryClient}>
      <ThemeProvider attribute="class" defaultTheme="system" enableSystem disableTransitionOnChange>
        <UserProvider>{children}</UserProvider>
      </ThemeProvider>
    </QueryClientProvider>
  );
}
\end{lstlisting}

\subsection{Components Interaction}

\paragraph{}The frontend follows React's unidirectional data flow to coordinate state between parent and child components. In some views, a parent component stores the main state and passes data or callbacks to child components through properties (\texttt{props}).

This pattern is used in the communication dashboard. The \texttt{ChatDashboard} component acts as the parent container and stores the state of the active conversation through \texttt{selectedConvId}. It coordinates two child components: \texttt{ConversationSidebar} and \texttt{ChatPage}.

The parent component passes the selected conversation state to its children and receives updates through callback functions, as shown in the layout definition below:

\begin{lstlisting}[caption={Parent state delegation inside ChatDashboard}, label={lst:chat-dashboard-interaction}]
{/* Sidebar (List of Messages) - Receives active ID and a callback */}
<div className="w-1/3 min-w-[300px] border-r border-zinc-800">
    <ConversationSidebar 
        profileId={parseInt(profileId)} 
        isCompany={isCompany}
        onSelectConversation={(id: number) => setSelectedConvId(id.toString())}
        activeConversationId={selectedConvId ? parseInt(selectedConvId) : undefined}
    />
</div>

{/* Chat Area - Dynamically rendered based on parent state */}
<div className="flex-1 bg-zinc-950/50">
    {selectedConvId ? (
        <ChatPage id={selectedConvId} />
    ) : (
        <div className="h-full flex flex-col items-center justify-center">
            <p className="text-lg font-medium">Select a conversation to start chatting</p>
        </div>
    )}
</div>
\end{lstlisting}

In this design, the \texttt{ConversationSidebar} child component triggers the \texttt{onSelectConversation} callback whenever a user interacts with a conversation item. This action instantly updates the parent state (\texttt{selectedConvId}). As a result, the parent component updates the selected conversation state and re-renders the relevant child components. The sidebar updates the selected conversation indicator, and the \texttt{ChatPage} displays the conversation associated with the selected identifier.


\subsection{API Interactions and Service Layer}
\paragraph{}The frontend uses a service layer to separate API communication from presentation components. Components do not call API endpoints directly. Instead, they use service classes that encapsulate network requests, interfaces and API paths.

Components can request data through React's \texttt{useEffect} hook when data must be loaded during component initialization or when relevant state values change. This hook allows the component to execute asynchronous requests, update loading states and store the returned data in local state.

An example of this pattern is the sector loading component. As shown in Listing~\ref{lst:sector-component-useEffect}, the component uses an asynchronous function inside \texttt{useEffect} to load the available sectors when the component is initialized:
\paragraph{}
\begin{lstlisting}[caption={Component data fetching via useEffect}, label={lst:sector-component-useEffect}]
useEffect(() => {
    async function fetchSectors() {
        try {
            const data = await sectorService.getAllSectors();
            setAvailableSectors(data);
        } catch (err) {
            console.error("Error loading sectors:", err);
        } finally {
            setLoadingSectors(false);
        }
    }
    fetchSectors();
}, []);
\end{lstlisting}

The \texttt{SectorService} class encapsulates the low-level network communication. By implementing a standardized service interface (\texttt{ISectorService}) and relying on an internal centralized \texttt{ApiClient} abstraction alongside structured route dictionaries (\texttt{API\_ENDPOINTS}), the service provides strongly typed data contracts to the user interface, as detailed below:

\begin{lstlisting}[caption={Sector Service layer implementation}, label={lst:sector-service-implementation}]
import ISectorService, { Sector } from "../interfaces/ISectorService";
import { ApiClient } from "./apiClient";
import { API_ENDPOINTS } from "./apiEndpoints";

export interface Sector {
    Id: number;
    Name: string;
}

class SectorService implements ISectorService {
    private apiClient = new ApiClient();

    async getAllSectors(): Promise<Sector[]> {
        const response = await this.apiClient.get<Sector[]>(API_ENDPOINTS.sectors.getAll);
        return response || [];
    }
}

export default new SectorService();
\end{lstlisting}

This organization avoids repeating API request logic inside multiple components. If an endpoint path changes or if request configuration needs to be updated, the change can be made in the \texttt{ApiClient} or in the \texttt{API\_ENDPOINTS} definitions, without modifying each component that consumes the service.

\section{Contexts} \label{sec:contexts_web}
\paragraph{}In web applications, particularly those using meta-frameworks such as Next.js, which combine server-side rendering with client-side hydration, sharing state across nested components can become complex. In the React ecosystem, contexts are used to share data and state between components without the need to pass props through the entire component tree (\textit{prop-drilling}). In this project, React's Context API is used to manage shared state, including user information, identity-related data and the SignalR connection used by the messaging components.

The \texttt{SignalRContext} provides a shared connection for the messaging components of Hubly. Instead of opening separate network connections in different views, such as the conversation list sidebar and the active chat view, this context creates and maintains a single bi-directional WebSocket connection with the backend event hub (\texttt{/api/hubly-events}).

This context works as a centralized connection manager. It avoids creating multiple connections for the same user session and allows chat-related components to reuse the same SignalR connection when required.

To implement this behavior, a \texttt{SignalRProvider} component was created. It wraps the application layouts that require real-time communication, such as creator and company chat routes. This component initializes the connection, configures automatic reconnection, handles connection errors and exposes the hub connection to nested components. The return statement of the \texttt{SignalRProvider} component is implemented as follows:

\begin{lstlisting}[caption={SignalRProvider implementation snippet}, label={lst:signalr-provider}]
    return (
        <SignalRContext.Provider value={{ connection, isConnected }}>
            {children}
        </SignalRContext.Provider>
    );
\end{lstlisting}

As shown above, the provider supplies the \texttt{HubConnection} object together with a boolean flag, \texttt{isConnected}, which indicates whether the client is currently connected. When the provider is mounted within a layout, it starts the connection asynchronously.

A custom hook called \texttt{useSignalR} was created to allow components to access the SignalR context. This hook wraps the use of React's \texttt{useContext}, allowing components such as message feeds or navigation elements to access the shared connection when required. A typical invocation of this hook inside active views is shown below:

\begin{lstlisting}[caption={Consuming the useSignalR hook}, label={lst:use-signalr-consumption}]
const { connection, isConnected } = useSignalR();
\end{lstlisting}

This hook is used across the messaging components. For instance, the \texttt{ChatPage} uses it to join topics, such as \texttt{JoinTopic}, and listen to events such as \texttt{NewMessage} or \texttt{MessageUpdated}, updating the interface when those events are received. The \texttt{ConversationSidebar} uses the same connection instance to listen for \texttt{SidebarUpdate} events, allowing unread message counts and preview information to be updated when relevant events are received.

The \texttt{useSignalR} hook checks whether it is being used inside a \texttt{SignalRProvider}. If the context is not available, the hook throws an error during runtime:

\begin{lstlisting}[caption={useSignalR hook implementation}, label={lst:use-signalr-hook}]
export const useSignalR = () => {
    const context = useContext(SignalRContext);
    if (!context) {
        throw new Error("useSignalR must be used within a SignalRProvider");
    }
    return context;
};
\end{lstlisting}

In addition to the real-time communication context, other contexts were implemented to separate concerns and manage shared state in different parts of the application:

\begin{itemize}
\item \texttt{UserContext} (\texttt{useUser}): Stores authenticated user information, including the user's profile and role. It is used by components that require access to the current user's session state or identity-related information.
\item \texttt{DashboardContext} (\texttt{useDashboardContext}): Defines a shared state scope for the main dashboard layout. It manages state used across dashboard components, such as loading states associated with asynchronous data loading, including recommendation feeds and trending content sections.
\end{itemize}

\section{Middleware} \label{sec:middleware_web}
\paragraph{}To support navigation and client-side route control, the application implements a custom Next.js middleware that processes incoming requests before they reach the rendering phase. This mechanism operates only on frontend page routes, directing users to the appropriate views based on their session state without interfering with backend API operations.

The authentication token is stored in a cookie configured with the \texttt{HttpOnly} attribute, which prevents client-side JavaScript from accessing its value and reduces exposure to Cross-Site Scripting (XSS) attacks. Since the middleware runs on the server side during the request lifecycle, it can read the token from the request cookies. At this layer, the middleware only checks whether the token exists. It does not validate the token structure or expiration date, since this validation is performed by the backend when protected API endpoints are called. If a protected route is requested and the token is absent, the user is redirected to the landing page. Conversely, if a user with an authentication token accesses public pages such as registration routes, the user is redirected to the main dashboard.

\begin{lstlisting}[caption={Middleware routing controls}, label={lst:middleware_frontend_web}]
const publicRoutes = ['/', '/register', '/register/confirmEmail'];

export function middleware(request: NextRequest) {
    const { pathname } = request.nextUrl;
    const isPublicRoute = publicRoutes.some(route => pathname === route);
    const token = request.cookies.get('token')?.value;

    if (!isPublicRoute && !token) {
        return NextResponse.redirect(new URL('/', request.url));
    }

    if ((pathname === '/' || pathname === '/register') && token) {
        return NextResponse.redirect(new URL('/dashboard', request.url));
    }

    return NextResponse.next();
}

export const config = {
    matcher: ['/((?!api|_next|.*\\..*).*)'],
};
\end{lstlisting}

The middleware evaluates frontend page requests according to the requested path and the presence of the authentication token in the request cookies. Based on this information, it redirects users when necessary and allows the request to continue when no routing rule applies. This provides an initial route-level check for protected frontend pages, while authentication and authorization for API operations remain handled by the backend.

\subsection{Architecture Components}

\paragraph{}\textbf{Route classification:}
The \texttt{publicRoutes} array defines frontend pages that can be accessed without authentication, including the home page (\texttt{/}), user registration (\texttt{/register}) and email confirmation (\texttt{/register/confirmEmail}) routes. This centralized configuration allows public routes to be modified in one place.

\paragraph{}\textbf{Selective route matching:}
The \texttt{matcher} configuration ensures that the middleware only processes frontend page requests while excluding:
\begin{itemize}
\item API routes (\texttt{/api/*});
\item Next.js internal routes (\texttt{/\_next/*});
\item Static assets, such as files with extensions like \texttt{.css}, \texttt{.js} or \texttt{.png}.
\end{itemize}

This prevents the middleware from interfering with API requests and static resource delivery.

\paragraph{}\textbf{Token-based route check:}
The middleware reads the authentication token from HTTP cookies to determine whether the request is associated with an authenticated session. This check is performed during server-side request handling and is used only for frontend route redirection.

\paragraph{}\textbf{Page redirection:}
The middleware applies redirection rules based on the requested route and the presence of the authentication token:
\begin{itemize}
\item Users without an authentication token who attempt to access protected frontend pages are redirected to the home page.
\item Users with an authentication token who access the home page or registration pages are redirected to the dashboard.
\end{itemize}

\paragraph{}\textbf{Request continuation:}
When no redirection condition is met, the middleware allows the request to proceed normally using \texttt{NextResponse.next()}.

\paragraph{}This middleware is limited to frontend route redirection. Authentication and authorization for API operations remain handled by the backend.
