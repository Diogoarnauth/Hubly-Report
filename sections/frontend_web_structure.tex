\paragraph{}To maintain a clean separation of concerns and ensure scalability, the frontend architecture is divided into three primary directories:

\begin{itemize}
    \item \textbf{app:} This directory serves as the structural foundation of the platform, utilizing the Next.js App Router for file-system-based routing. Rather than handling imperative user navigation, it defines the URL endpoints of the application. The files within this directory act as lightweight entry points that extract URL parameters, define route-specific layouts, wrap pages with necessary Context Providers (such as injecting a \texttt{SignalRProvider} for chat routes), and delegate the actual UI rendering and complex logic to dedicated components.
    \item \textbf{components:} This folder acts as a repository for modular, reusable User Interface (UI) elements. It isolates the visual building blocks from the core routing logic.
    \item \textbf{services:} Centralizes all external communications. This directory handles API requests, data fetching, and core business logic, ensuring that UI components remain lightweight and focused solely on rendering data.
\end{itemize}

\section{Components Architecture}
\paragraph{}Components form the structural foundation of our frontend. By designing them to be highly decoupled from specific pages, we ensure maximum reusability and maintainability across the entire application.

We adopted a modular approach for the \texttt{components} folder to improve code maintainability. General-purpose elements that appear across multiple views, such as buttons and form inputs, are centralized in the \texttt{ui} subdirectory. Utilizing the \texttt{shadcn/ui} library for these shared components allowed us to enforce a standardized and cohesive user interface.

Conversely, components that are tailored to a specific feature are grouped into dedicated, context-specific folders. For instance, the \texttt{chat} and \texttt{search} directories house specialized components such as \texttt{ChatDashboard} and \texttt{CreatorSearch}, ensuring that domain-specific logic remains neatly compartmentalized and easy to locate.
\section{Global State and Contexts} \label{sec:contexts_web}

\paragraph{}In our application, certain data must be instantly accessible across almost every view. The most critical piece of global information is the authenticated user's session data (specifically their \texttt{id}, \texttt{name}, and \texttt{role} as a creator or company). This information is heavily utilized by global components like the \texttt{Navbar}, which adapts its UI and navigation links based on the active user profile.

To handle this efficiently without making redundant API calls (such as repeatedly fetching the user's full profile on every page load), we implemented a highly optimized state management architecture combining React's Context API with \textbf{TanStack React Query}.

\subsection{Server State Caching with React Query}
\paragraph{}We rely on React Query for server-state management. As demonstrated in our \texttt{UserProvider}, we utilize the \texttt{useQuery} hook to fetch the current user's minimal details. React Query automatically caches this response. By configuring a \texttt{staleTime} of 30 minutes, we guarantee that as the user navigates the platform, the application instantly retrieves their details from the local cache rather than constantly querying the backend.

\begin{lstlisting}[caption={UserProvider utilizing React Query}, label={lst:user-provider}]
export const UserProvider = ({ children }: { children: React.ReactNode }) => {
    const queryClient = useQueryClient();

    const { data: user, isLoading, refetch } = useQuery({
        queryKey: ['user'],
        queryFn: async () => {
            const userData = await usersService.getCurrentUser();
            return userData ? {
                id: userData.id,
                name: userData.name,
                email: userData.email,
                role: userData.role 
            } : null;
        },
        staleTime: 1000 * 60 * 30, // Maintains data fresh for 30 minutes
        retry: false,
    });
    // ...
};
\end{lstlisting}

\subsection{Context Distribution}
Once React Query secures and caches the data, we use React's Context API to distribute it seamlessly throughout the component tree. We established a \texttt{UserContext} accompanied by a custom hook named \texttt{useUser}. This abstraction allows any component (like the \texttt{Navbar}) to cleanly access the user object, loading indicators, and authentication methods (such as \texttt{logout} or \texttt{refreshUser}) without prop-drilling or concerning itself with data-fetching logic.

To ensure these contexts operate application-wide, we centralized them within a \texttt{Providers} wrapper. This wrapper encapsulates the Next.js \texttt{RootLayout}, injecting the \texttt{QueryClientProvider}, \texttt{ThemeProvider}, and our \texttt{UserProvider} into the very top of the DOM hierarchy.

\begin{lstlisting}[caption={Global Providers Setup}, label={lst:providers-setup}]
export function Providers({ children }: { children: React.ReactNode }) {
  const [queryClient] = useState(() => new QueryClient());
  return (
    <QueryClientProvider client={queryClient}>
      <ThemeProvider attribute="class" defaultTheme="system" enableSystem disableTransitionOnChange>
        <UserProvider>{children}</UserProvider>
      </ThemeProvider>
    </QueryClientProvider>
  );
}
\end{lstlisting}

\subsection{Components Interaction}
\paragraph{}Our frontend design strictly follows React's unidirectional data flow to coordinate behaviors between complex view structures. Instead of letting deeply nested views manage isolated instances of data, a master parent component encapsulates the primary state and orchestrates its sub-components using specialized properties (\texttt{props}) and event callbacks.

A clear architectural demonstration of this pattern is found in the communication dashboard. The \texttt{ChatDashboard} component acts as the parent container, maintaining the state of the active chat channel via the \texttt{selectedConvId} hook. It manages two highly specialized child components: the \texttt{ConversationSidebar} and the \texttt{ChatPage}.

To achieve seamless interoperability without tight coupling, the parent component injects state down to its children and listens for updates through structural callbacks, as shown in the layout definition below:

\begin{lstlisting}[caption={Parent state delegation inside ChatDashboard}, label={lst:chat-dashboard-interaction}]
{/* Sidebar (List of Messages) - Receives active ID and a callback */}
<div className="w-1/3 min-w-[300px] border-r border-zinc-800">
    <ConversationSidebar 
        profileId={parseInt(profileId)} 
        isCompany={isCompany}
        onSelectConversation={(id: number) => setSelectedConvId(id.toString())}
        activeConversationId={selectedConvId ? parseInt(selectedConvId) : undefined}
    />
</div>

{/* Chat Area - Dynamically rendered based on parent state */}
<div className="flex-1 bg-zinc-950/50">
    {selectedConvId ? (
        <ChatPage id={selectedConvId} />
    ) : (
        <div className="h-full flex flex-col items-center justify-center">
            <p className="text-lg font-medium">Select a conversation to start chatting</p>
        </div>
    )}
</div>
\end{lstlisting}

In this design, the \texttt{ConversationSidebar} child component triggers the \texttt{onSelectConversation} callback whenever a user interacts with a conversation item. This action instantly updates the parent state (\texttt{selectedConvId}). Consequently, the parent triggers a re-render, automatically refreshing the visual selection highlight inside the sidebar while simultaneously safe-mounting or updating the \texttt{ChatPage} viewport with the freshly selected conversation context.


\subsection{API Interactions and Service Layer}
\paragraph{}To separate business and data-fetching logic from the presentation layer, our frontend architecture enforces a strict separation of concerns using a dedicated service tier. Visual components do not query endpoints directly; instead, they interact with centralized service singletons that abstract network requests, interfaces, and API paths.

Components consume this data lifecycle primarily through React's \texttt{useEffect} hook. This hook triggers asynchronous data collection when a component is mounted or when specific tracking states shift, safely managing internal loading flags and populating local state vectors upon successful response resolution.

A clear implementation of this decoupling pattern can be observed in the sector categorization module. As demonstrated in Listing~\ref{lst:sector-component-useEffect}, the component uses a clean asynchronous sequence wrapper to handle sector ingestion on lifecycle initialization:

\begin{lstlisting}[caption={Component data fetching via useEffect}, label={lst:sector-component-useEffect}]
useEffect(() => {
    async function fetchSectors() {
        try {
            const data = await sectorService.getAllSectors();
            setAvailableSectors(data);
        } catch (err) {
            console.error("Error loading sectors:", err);
        } finally {
            setLoadingSectors(false);
        }
    }
    fetchSectors();
}, []);
\end{lstlisting}

Behind this interaction, the \texttt{SectorService} class encapsulates the low-level network communication. By implementing a standardized service interface (\texttt{ISectorService}) and relying on an internal centralized \texttt{ApiClient} abstraction alongside structured route dictionaries (\texttt{API\_ENDPOINTS}), the service provides strongly typed data contracts to the user interface, as detailed below:

\begin{lstlisting}[caption={Sector Service layer implementation}, label={lst:sector-service-implementation}]
import ISectorService, { Sector } from "../interfaces/ISectorService";
import { ApiClient } from "./apiClient";
import { API_ENDPOINTS } from "./apiEndpoints";

export interface Sector {
    Id: number;
    Name: string;
}

class SectorService implements ISectorService {
    private apiClient = new ApiClient();

    async getAllSectors(): Promise<Sector[]> {
        const response = await this.apiClient.get<Sector[]>(API_ENDPOINTS.sectors.getAll);
        return response || [];
    }
}

export default new SectorService();
\end{lstlisting}

This architecture offers major benefits over standard inline fetch approaches. If an API endpoint structure changes or if custom headers need to be appended globally, modifications are constrained to the network layer configs (\texttt{ApiClient} or \texttt{API\_ENDPOINTS}), completely neutralizing side effects over the visual DOM tree and rendering components.

\section{Contexts} \label{sec:contexts_web}
\paragraph{}In modern web applications, particularly those utilizing meta-frameworks like Next.js that blend server-side rendering with client-side hydration, sharing reactive state across deeply nested components can become complex. In the React ecosystem, contexts are used to share data and state between components without the need to pass props through the entire component tree (\textit{prop-drilling}). In our implementation, we strategically leverage React's Context API to manage global state, handle identity validation, and, most importantly, provide a unified real-time infrastructure through the \texttt{SignalRContext}.

The \texttt{SignalRContext} acts as a shared, persistent architectural foundation for the entire messaging ecosystem of Hubly. Instead of forcing separate views, such as the conversation list sidebar and the active chat viewport, to open independent network connections, this context instantiates and maintains a single, global bi-directional WebSocket connection with our backend event hub (\texttt{/api/hubly-events}). 

We treat this context as a centralized connection manager implementing a Singleton-like behavior. This approach optimizes client and server resources by avoiding redundant handshakes, ensuring that whenever a user navigates between chat modules, the underlying stream remains active, synchronized, and ready to intercept server-driven events.

To implement this infrastructure, we developed a \texttt{SignalRProvider} component. It wraps the specific layout structures within the application that require real-time capabilities (such as creator and company chat sub-routes). This component initializes the connection lifecycle, configures automatic reconnection strategies, handles connection errors, and exposes the active hub instance to all nested consumers. The return statement of the \texttt{SignalRProvider} component is implemented as follows:

\begin{lstlisting}[caption={SignalRProvider implementation snippet}, label={lst:signalr-provider}]
    return (
        <SignalRContext.Provider value={{ connection, isConnected }}>
            {children}
        </SignalRContext.Provider>
    );
\end{lstlisting}

As shown above, the provider supplies the underlying \texttt{HubConnection} object along with a reactive boolean flag (\texttt{isConnected}) that dictates whether the client is currently online. When the provider is mounted within a layout, it automatically kicks off the connection startup sequence asynchronously.

To streamline the consumption of this real-time stream inside our functional components, we exposed a custom hook called \texttt{useSignalR}. This hook abstracts away the internal mechanics of React's \texttt{useContext}, allowing any message feed or navigation bar to instantly tap into the persistent connection. A typical invocation of this hook inside active views looks as follows:

\begin{lstlisting}[caption={Consuming the useSignalR hook}, label={lst:use-signalr-consumption}]
const { connection, isConnected } = useSignalR();
\end{lstlisting}

This hook is heavily utilized across our messaging components. For instance, the \texttt{ChatPage} uses it to invoke streaming topics (e.g., \texttt{JoinTopic}) and listen to incoming payloads like \texttt{NewMessage} or \texttt{MessageUpdated} to update the UI instantly. Simultaneously, the \texttt{ConversationSidebar} consumes the exact same connection instance to listen for \texttt{SidebarUpdate} events, keeping unread message counts and preview snippets dynamically synchronized in the background.

The defensive implementation of the \texttt{useSignalR} custom hook ensures architectural integrity by verifying the existence of the context boundary during runtime:

\begin{lstlisting}[caption={useSignalR hook implementation}, label={lst:use-signalr-hook}]
export const useSignalR = () => {
    const context = useContext(SignalRContext);
    if (!context) {
        throw new Error("useSignalR must be used within a SignalRProvider");
    }
    return context;
};
\end{lstlisting}

In addition to the real-time communication infrastructure, other vital contexts were implemented to separate concerns and govern different lifecycles of the Hubly ecosystem:

\begin{itemize}
    \item \texttt{UserContext} (\texttt{useUser}): Acts as the application's global identity state and access guard. It caches the authenticated user's profile and roles, serving as a client-side routing middleware that redirects incomplete sessions to the onboarding flow or restricts unauthorized access to core dashboards.
    \item \texttt{DashboardContext} (\texttt{useDashboardContext}): Serves as a localized state scope for the main dashboard layout. It manages shared layout behaviors, such as global loading states (\texttt{isLoading}) across separate asynchronous components, including recommendation feeds and trending content carousels.
    \item \texttt{And some more...}
\end{itemize}


\section{Middleware} \label{sec:middleware_web}
\paragraph{}To optimize navigation and enforce client-side routing boundaries, the application implements a custom Next.js middleware that intercepts incoming requests before they reach the rendering phase. This mechanism operates strictly on frontend page routes, ensuring that users are seamlessly directed to the appropriate views based on their session state without introducing overhead or interfering with backend API operations. 

Architecturally, the authentication token is stored within a cookie configured with the \texttt{HttpOnly} attribute to prevent client-side access and mitigate Cross-Site Scripting (XSS) vulnerabilities. However, since the middleware executes exclusively on the server-side during the request lifecycle, it can securely evaluate the presence of the token from the HTTP request headers. At this layer, the middleware performs a lightweight, non-blocking evaluation: it simply verifies whether the token exists. It does not cryptographically validate the token's structural integrity or expiration date, as this computationally expensive verification is properly deferred to the backend services during subsequent API data fetches. If a protected route is requested and the token is absent, the user is proactively redirected to the landing page. Conversely, if an authenticated user attempts to access redundant public registration forms, they are forwarded directly to the main dashboard.

\begin{lstlisting}[caption={Middleware routing controls}, label={lst:middleware_frontend_web}]
const publicRoutes = ['/', '/register', '/register/confirmEmail'];

export function middleware(request: NextRequest) {
    const { pathname } = request.nextUrl;
    const isPublicRoute = publicRoutes.some(route => pathname === route);
    const token = request.cookies.get('token')?.value;

    if (!isPublicRoute && !token) {
        return NextResponse.redirect(new URL('/', request.url));
    }

    if ((pathname === '/' || pathname === '/register') && token) {
        return NextResponse.redirect(new URL('/dashboard', request.url));
    }

    return NextResponse.next();
}

export const config = {
    matcher: ['/((?!api|_next|.*\\..*).*)'],
};
\end{lstlisting}

By intercepting top-level document requests, the middleware evaluates the user's navigational context through these secure cookie lookups. It handles automated adjustments to the application's flow in real-time, delivering a fluid user experience while establishing initial guardrails for protected layout modules.

\subsection{Architecture Components}
\paragraph{}\textbf{Route Classification System:}
The publicRoutes array defines frontend pages accessible without authentication, including the home page (/), user registration (/register), and email confirmation (/register/confirmEmail) routes. This centralized configuration allows for easy modification of public access permissions as the application grows.

\textbf{Selective Route Matching:}
The matcher configuration ensures the middleware only processes frontend page requests while excluding:
\begin{itemize}
\item API routes (\texttt{/api/*})
\item Next.js internal routes (\texttt{/\_next/*})
\item Static assets (files with extensions like \texttt{.css}, \texttt{.js}, \texttt{.png}, etc.)
\end{itemize}
This selective approach prevents interference with API functionality and static resource serving.

\textbf{Token-Based Authentication Check:}
The middleware extracts authentication tokens from HTTP cookies to determine user authentication status. This approach provides a server-side validation mechanism that works seamlessly with Next.js's server-side rendering capabilities.

\textbf{Intelligent Page Redirection:}
The system implements smart redirection logic for optimal user experience:
\begin{itemize}
\item Unauthenticated Access Protection: Users without valid tokens attempting to access protected frontend pages are redirected to the home/login page, preventing access to sensitive areas like user dashboards or account pages.
\item Authentication Flow Optimization: Users with valid tokens who navigate to login or registration pages are automatically redirected to the dashboard, eliminating redundant authentication steps and improving user flow.
\end{itemize}

\textbf{Request Continuation:}
When no redirection conditions are met, the middleware allows requests to proceed normally using NextResponse.next(), maintaining standard Next.js routing behavior for all appropriate scenarios.

This middleware architecture focuses specifically on frontend user experience and page-level access control, while API security remains the responsibility of individual endpoint implementations.
