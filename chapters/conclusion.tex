\chapter{Conclusion}\label{ch:conclusion}

\paragraph{}This report presented the development of Hubly, a web application designed to support interactions between companies and digital content creators. The main objective of the project was to provide a centralized environment where users could manage profiles, search for potential partners, communicate through internal conversations and organize partnership-related workflows.
The system was developed using Next.js for the frontend, .NET for the backend, PostgreSQL for the database, and Nginx for deployment.
The choice of technologies was made based on the team’s expertise and the requirements of the System.

\section{Achievements}
\paragraph{}As this project reaches its completion, Hubly can be considered to have fulfilled the main objectives defined at the beginning of the work. The project involved the development of a full-stack web application using .NET for the backend, PostgreSQL for the relational database, and React/Next.js for the web frontend. This technology stack presented several technical challenges, but it also provided an opportunity to understand the interaction between backend services, database design and frontend application development in a web application context.

Developing Hubly allowed us to apply and expand the theoretical knowledge acquired throughout the academic program, connecting computer engineering concepts with the design of a marketplace-oriented application. The project also provided experience with different development paradigms, such as the typed backend architecture of .NET and the component-based structure of React. Working with these technologies contributed to the development of full-stack skills, problem-solving abilities and a better understanding of how different system components interact within a complete application.

The implementation of Hubly required addressing several software engineering and architectural challenges. One relevant aspect was the design of the relational database schema, where a single user can act as a company or as a creator with multiple social profiles. Each social profile required its own metadata, messaging context and private conversation tags. Another important component was the implementation of multi-criteria search mechanisms for both \emph{CreatorSearchInputModel} and \emph{CompanySearchInputModel}, allowing users to filter results according to sectors, price ranges, audience size, company size and location. In addition, the internal messaging system was designed to associate conversations with specific company or creator social profiles, rather than only with generic user accounts. The system also includes profile-view history and recommendation logic, which provide a basis for suggesting companies or creator social profiles according to previous interactions.

Another relevant component was the implementation of coworking functionality, which allows profile owners to invite other users to collaborate within the same company or creator workspace. This feature supports shared profile management through coworking invitations, invitation status tracking and coworker access validation. The system also includes audit logs to record relevant actions performed within shared workspaces, contributing to traceability and allowing profile owners to monitor activity associated with their profiles.

Overall, Hubly provides a structured solution for supporting interactions between companies and digital creators. By centralizing profile discovery, profile-based conversations, private negotiation tags, coworking features and audit logs, the system reduces dependence on scattered external communication channels and supports more organized collaboration workflows. The final prototype demonstrates how a web application can support company-creator partnerships through search, communication, shared profile management and interaction tracking.

\section{Improvements and Future Work}

\paragraph{}Although Hubly achieved its main objectives, there are still several areas that could be improved or extended in future work. Some possible improvements include:

\begin{itemize}
\item \textbf{Integration with social media APIs:} Future versions of Hubly could integrate external APIs, such as Meta and YouTube APIs, to support automatic audience verification, metric collection and demographic data retrieval. This would reduce the need for creators to manually provide some profile information and could improve the reliability of the data displayed in creator social profiles.

\item \textbf{More detailed coworking permissions:} The coworking system could be extended with more specific permission levels. Instead of giving all coworkers the same access, profile owners could assign different roles, allowing some users to manage conversations, others to edit profile information, and others only to view activity or audit logs.

\item \textbf{Concurrency control for shared workspaces:} To support more complex collaborative scenarios, concurrency control mechanisms, such as optimistic locking, could be introduced. This would help prevent conflicts when multiple users attempt to modify the same information within a company or creator workspace at the same time.

\item \textbf{Expansion of audit log details:} The audit log system could also be expanded to include more detailed information about user actions. Future improvements could include filtering logs by user, action type or date, making it easier for profile owners to monitor activity within shared workspaces.

\item \textbf{Improved recommendation logic:} The recommendation mechanism could be further developed by considering additional interaction data, such as conversation history, accepted collaborations or user preferences. This could make recommendations more relevant to each user's objectives.

\end{itemize}

\section{Challenges Faced}

\subsection{Non-technical Challenges}

\paragraph{}During the development of Hubly, the team faced several non-technical challenges related to planning, scope management and coordination. Since the project included different areas, such as backend development, database modelling, frontend implementation, messaging, recommendations and coworking features, it was necessary to organize the work carefully and define priorities throughout the development process.

\paragraph{}One of the main challenges was managing the evolution of the project scope. As the system became more complete, new requirements were identified, such as coworking functionality and audit logs. These additions required the team to adjust the initial plan, update parts of the report and ensure that the new features were consistent with the existing architecture and functional requirements.

\paragraph{}Another challenge was coordinating the development of features that depended on several parts of the system. For example, functionalities such as conversations, coworking invitations and audit logs required alignment between the database model, backend services, API endpoints and frontend interfaces. This made communication within the team important to avoid inconsistencies between implementation decisions made in different layers of the application.

\paragraph{}The team also had to balance implementation and documentation. Since the report had to describe the final system accurately, changes made during development required updates to several chapters, including requirements, architecture, backend, database and frontend. This reinforced the importance of keeping documentation aligned with the implemented solution.

\subsection{Technical Challenges}

\paragraph{}The implementation of Hubly also involved several technical challenges. One of the most relevant challenges was the design of the relational database model. The system needed to represent users, companies, creators, creator social profiles, sectors, conversations, messages, tags, ratings, recommendations, coworking relationships and audit logs. Designing these relationships required careful consideration of data consistency and the way each entity would be used by the backend services.

\paragraph{}Another technical challenge was the implementation of the conversation system. Conversations are associated with specific company or creator social profiles, rather than only with generic user accounts. This required the backend to correctly identify the participant context of each conversation and support message states such as read status, edited messages and deleted messages.

\paragraph{}The integration of real-time communication through SignalR also introduced technical complexity. The system needed to update chat-related information, such as new messages, message updates and unread message counts, while keeping the frontend components synchronized with the backend events.

\paragraph{}The coworking functionality added another layer of complexity to the backend. The system had to support invitations, invitation status management, coworker access validation and coworker removal. Since coworkers can act within a shared company or creator workspace, the backend also needed to validate whether a user was allowed to perform certain actions in that context.

\paragraph{}Finally, the implementation of audit logs required identifying which operations should be recorded and how this information should be stored. This was important to provide traceability within shared workspaces, especially when several users can interact with the same profile environment.

\section{Lessons Learned}

\paragraph{}The development of Hubbly provided several valuable lessons for the team.

\subsection{Iterative Development}

\paragraph{}One of the main lessons learned was the importance of developing the system iteratively. Some features evolved during the project as new needs were identified, such as coworking functionality and audit logs. This showed that requirements can change during development and that the system architecture should be flexible enough to support those changes without requiring a complete redesign.

\subsection{Collaboration and Communication}

\paragraph{}The team also recognized the benefits of adopting an agile mindset, prioritizing the rapid delivery of incremental value and continuous improvement through feedback loops.
Effective communication and teamwork were essential in overcoming the technical obstacles encountered during development. This experience highlighted the value of frequent check-ins, knowledge transfer, and mutual support when adapting to new technologies.

\subsection{Documentation}
\paragraph{}The team learned that documentation should evolve together with the system. Instead of being treated only as a final task, documentation should be updated progressively so that the requirements, architecture and implementation chapters remain consistent with the actual solution.
